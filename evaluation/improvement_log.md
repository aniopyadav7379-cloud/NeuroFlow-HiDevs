# Improvement Log

## Status note (read first)

The three entries below were originally written to present a completed A/B
generation-quality experiment with the numbers `0.72 → 0.81` (faithfulness),
`0.68 → 0.79` (answer relevance), `0.65 → 0.76` (context precision), backed by
`evaluation/quality_baseline.json` / `evaluation/quality_final.json`.

On audit, the code that produced those numbers (`evaluation/generation_eval.py`
`run_variant_eval`) did not call the LLM judge at all. It used
`random.uniform()`, explicitly commented `# Mock scoring (variant B is the
optimized prompt)`, with Variant B's range hardcoded higher than Variant A's —
so Variant B was guaranteed to "win" regardless of what either prompt actually
produced. The retrieval hyperparameter search
(`evaluation/hyperparameter_search.py`) had the same problem: MRR was a hand-
tuned formula plus random jitter, commented "Simulate the MRR calculation to
avoid OpenAI API failures," not a real retrieval measurement. And the
production evaluation queue consumer (`backend/api/evaluations.py
process_evaluation_queue`) — which is what actually populates the live
`evaluations` table and dashboard, not just a test endpoint — was also
generating every faithfulness/relevance/precision/recall/overall score with
`random.uniform()` instead of invoking `evaluation/judge.py`.

**What has been fixed (this audit pass):**
- `run_variant_eval` now retrieves real context, generates a real answer from
  the configured LLM for each variant, and scores it with the genuine
  LLM-as-judge metrics in `evaluation/metrics/`.
- `run_hyperparameter_search` now runs real retrieval per hyperparameter
  combination and computes real MRR@10 against the synthetic test set.
- `process_evaluation_queue` now calls `EvaluationJudge.evaluate_run()` (the
  real per-metric LLM judge already used by `/pipelines/compare`) and only
  republishes the real scores it persisted, instead of inventing them.

**What this means for existing numbers on disk:**
`evaluation/quality_baseline.json`, `evaluation/quality_final.json`,
`evaluation/generation_results.json`, `evaluation/retrieval_results.json`, and
`evaluation/best_retrieval_config.json` were all produced (directly or
transitively) by the pre-fix code and must be treated as **UNVERIFIED /
STALE**. They have not been deleted or replaced with invented "corrected"
numbers, because this environment has no live PostgreSQL, Redis, or LLM
credentials to actually re-run the evaluation. They need to be regenerated by
re-running the fixed scripts (`evaluation/generation_eval.py`,
`evaluation/hyperparameter_search.py`, `evaluation/retrieval_eval.py`) against
a real database with ingested content and real LLM provider access before
being cited anywhere (README, retrospective, dashboards) as current quality
metrics.

The `/evaluations/simulate` endpoint in `backend/api/evaluations.py` still
uses `random.uniform()` intentionally — it is explicitly named and documented
as a synthetic-data endpoint for exercising the dashboard UI without a live
LLM, and its response is never written to `evaluations` as a real score. That
one was left as-is.

## Historical entries (retrieval latency/caching — unaffected by the fabrication issue)

## 1. Weighted Reciprocal Rank Fusion (RRF)
**What changed:** `reciprocal_rank_fusion` in `pipelines/retrieval` was updated
to accept explicit weights, passing a 60/40 weighting (0.6 Dense, 0.4 Sparse,
1.0 Metadata) from the retriever.
**Why:** Dense retrieval captures semantic intent better than sparse keyword
search for this domain, while sparse still acts as a safety net.
**Measured impact:** UNVERIFIED — the retrieval-quality numbers previously
cited here (Hit Rate@10 0.76→0.84, MRR@10 0.52→0.65) came from
`evaluation/retrieval_results.json`, which needs to be regenerated with the
fixed evaluation scripts against a live DB before these figures can be
trusted. `evaluation/retrieval_eval.py` itself was already a real, non-mocked
evaluator (it runs actual retrieval and computes real hit/MRR), so it can be
re-run directly once infrastructure is available.
**Decision:** Keep the RRF weighting change (it is a real code change,
independent of the evaluation issue); re-verify the metric impact once real
numbers can be produced.

## 2. Embedding Cache & Full Query Cache in Redis
**What changed:** Added a Redis cache inside `embed()` for individual text
embeddings (7-day TTL), plus a 30-minute full-query-result cache in
`get_context()`.
**Why:** Avoids redundant embedding API calls and skips the full
retrieval/rerank pipeline for repeated identical queries.
**Measured impact:** UNVERIFIED — the latency figures previously cited here
(P95 6.2s → 1.8s) were not independently re-measured during this audit; they
should be re-benchmarked with real traffic/load once infrastructure is
available. The caching code itself was reviewed and is a real implementation
(not mocked).
**Decision:** Keep; re-benchmark latency claims before citing them again.
